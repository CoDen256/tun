# smia-tts
- [smia tts provider data and ui] chose an adaptive saturation stop K = max(2, ceil(ln0.01/ln(1−draw/(pool+1)))) over a fixed K — because it bounds the chance of a missed word at 1% for any pool size (947: 20 zero-gain draws)
- [smia tts provider data and ui] chose a 120-request cap per (exercise, dialect) over 80 — because 947 alone needed 47 samples
- [smia tts provider data and ui] chose sequential 0.5–1.0 s pacing with one 90 s-timeout retry over parallel requests — because CALST answers in ~3.5 s and politeness outranks the ~15–20 h full-crawl duration
- [smia tts provider data and ui] chose cache key sha256([method,path,data,{dialect,sample}]) while keeping the legacy key for GETs and Oslo sample 0 — because the committed LAS cache is then reused without a request
- [smia tts provider data and ui] chose dialect discovery from /account/settings' `l2d` select (8 Norwegian dialects; 9–12 are other languages, excluded) over a hardcoded list — because it fails loudly if CALST changes
- [smia tts provider data and ui] chose crawling Oslo first, then the other 7 dialects, over one 8-dialect run — because Oslo alone carries every reported missing word and finishes in ~2.5 h
- [smia tts provider data and ui] chose MISS_EPSILON 0.001 over 0.01 and a circuit breaker that aborts the run after 10 consecutive failed requests (report printed, manifest not written, exit 3; 429 honours Retry-After with 5→10→20→40 s backoff, max 300 s) over unbounded retrying — because the design's reference is <0.1 % chance of any missed word (947: 30 zero-gain draws, a few more requests on ~36 pools) and a site-wide outage or login redirect must stop the crawl instead of hammering the server and recording 2,800 failures
- [smia tts provider data and ui] chose one dict.cc candidate per Norwegian recording, fetched by recording id via `speak.audio.v2.php?lang=rec&id=<recId>` with `voice` = the key's `<user>`, over voice-only-for-single-recording entries — because a live probe (stille, entry 383115) showed `lang=rec` returns exactly the keyed recording (bytes identical to the entry-level call for the sole lid81 take; two lid2 takes of one entry came back as two distinct files, one unreachable entry-level), and recording ids are global so each is fetched once per lookup
- [smia tts provider data and ui] chose adding a nullable verbatim `pygmalion_audio.text` column beside `match_key` over returning the casefolded `word` as `context` — because acceptance 3 requires `context: "Hallo!"` and `word` stores `hallo!`; NULL rows (pre-re-import) fall back to `word`
- [smia tts provider data and ui] chose backfilling `match_key` from `word` inside the migration (and backfilling NULL `text`/`match_key` on importer re-runs) over relying solely on the deploy's truncate + re-import — because bootstrap skips the import when the table is non-empty, which would leave tiers 2/3 dead until someone truncates
- [smia tts provider data and ui] chose a trailing-particle list of the required 16 plus `fra for etter tilbake hjem unna mot ved` over the bare minimum, and dropping parenthesised annotations in `normalize_match_key` (`deres (3. person)` → `deres`) — because tier 3/2 only fire after an exact miss and `context` labels the result
- [smia tts provider data and ui] chose ordering fuzzy candidates Oslo-first, then dialect, stored word, take over grouping by stored word first — because it keeps tier 1's established dialect order and makes several stored spellings of one key interleave predictably
